context 是有限的注意力预算。
与其每个 session 都重新解释背景，不如在 repo 里建立"可预测的读/写上下文约定"。

核心主张

LLM 的上下文窗口不是免费的——token 越多，注意力越稀薄（context rot）。所以只放从代码里看不出来的知识，其余让 AI 按需去读。

  • 约定分两层：general（repo 级，全局共享）+ per-task（复杂任务级，专属背景）。
  • 读：可预测的位置，AI 知道去哪找、先读哪个。
  • 写：明确的触发条件 + 清单，AI 知道何时记、记到哪、怎么记。

目录全貌：

repo/
├── AGENTS.md            # 协议：怎么读 / 怎么更新 / 指向哪
├── CONTEXT.md           # 背景：项目 / 结构 / 约定 / 决策 / 坑
├── tasks/
│   └── <slug>/          # 复杂任务专属目录
│       ├── index.md     # 入口 + 索引（有哪些资料 / 脚本 / 何时跑）
│       ├── background.md# 原始需求 + 决策 log
│       ├── status.md    # 当前状态 + 下一步 + 剩余
│       └── scripts/     # 确定性脚本（可选）
└── ...                  # 你的正常代码

General 层：AGENTS.md + CONTEXT.md

AGENTS.md —— 协议

只放协议：怎么读、怎么更新、指向哪。保持精简（<200 行），塞多了反而降低遵守度。

CONTEXT.md —— 背景

只放背景，分 5 节：① 这是什么项目 ② 目录结构 ③ 关键约定/技术栈 ④ 重要决策(带日期) ⑤ 坑/注意事项。

关键：CONTEXT.md 不自动加载。AGENTS.md 里写一句"项目背景见 CONTEXT.md，需要时读"。这就是 Anthropic 说的 just-in-time 加载——避免每个 session 都吞整份背景。

参考 Claude Code 的内存机制：MEMORY.md 索引在启动时加载（有 200 行/25KB 上限），详情放 topic 文件按需读。索引瘦、详情懒加载，是这个模式的核心。

Per-task 层：tasks/<slug>/

判定阈值：跨多 session、有多轮讨论、或实现周期 >1 天的任务才建目录。简单任务不建，别为一条命令建个目录。

核心洞察：一个复杂任务会产生三类更新节奏不同的信息，所以拆成三个文件，而不是塞进一个 knowledge.md：

  • 需求（会演化）
  • 决策/结论（append-only，累积）
  • 进度/状态（频繁刷新）

background.md 示例

## 原始需求
- 在 repo 里以好的方式记录上下文，general + per-task 两层。

## 决策 log（append-only，不重写历史）
### 2026-09-20
- 决定：general 层 = AGENTS.md(协议) + CONTEXT.md(背景，按需加载)。
- 决定：per-task 目录用 tasks/<slug>/，3 文件 + scripts/。
- 决定：更新协议 = 显式 + 触发词 + 每 ~5 轮清单，防噪只追加。

Recall Skill：自动触发回忆

项目级 memory 本身没有自动触发能力，但 skill 有。所以用一个 recall-memory skill，把触发词 + active task 列表写进 description，body 写"怎么读"。

skill 结构（.claude/skills/recall-memory/SKILL.md）：

---
name: recall-memory
description: 回忆本 repo 的项目级 memory...（触发词 + 触发场景写这里）
---

## Active tasks（触发词 → 目录）
- context-recording — 在 repo 里记录上下文的约定

## 怎么读
1. 先读 CONTEXT.md
2. 匹配 task 后读 tasks/<slug>/index.md → background.md → status.md

单一来源：触发词/task 映射只写在 skill 的 description，AGENTS.md 只留协议 + 指向 skill。改触发词只改一处。

  • 维护：tasks 少（<5）时手动更新 description；多了再用脚本扫描 tasks/ 重生成。
  • 分工：skill = 自动触发路径（增强），AGENTS.md 读取协议 = 兜底。

文件职责

文件 职责 更新节奏
index.md入口 + 索引（资料/脚本清单）文件增删时
background.md原始需求 + 决策 log决策产生时 append
status.md当前状态 + 下一步 + 剩余里程碑变化时
scripts/确定性脚本（如重生成图、跑 benchmark）任务确定后

读写协议

协议写进 AGENTS.md，触发词/路由写进 recall-memory skill 的 description。作为行为指导（跨 Claude Code / Codex / pi 多工具，不绑定某工具的 hook）。

触发（任一）

  • 显式：用户说"更新 task 上下文 / 记录一下 / 记到 background"。
  • 触发词：见 recall-memory skill 的 description（例：结论是 / 决定 / 记一下 / 更新背景 / 记住 / 继续 / 回忆）。
  • 自动：每 ~5 轮对话，或 session 结束前、/compact 前。

读：命中触发词或开新 session 时，触发 recall-memory skill 回忆（读 index.md 定位 task → background.md）；未触发时手动读。

执行 3 条清单

  1. 有新决策/结论/事实？→ append 到 background.md（带日期，精炼，不整段抄对话）。
  2. status.md 还反映当前状态吗？
  3. index.md 是否缺新文件/新脚本？

防噪规则：只记结论不记流水账；已有条目只追加、不重写。重写历史会丢掉"为什么当初这么定"的上下文。

与 Skill 的关系

借结构，不合并。task 目录本质是项目级 / repo 级 memory，不是 skill。

skill 是 general 的：全局、可复用，靠描述/名字自动触发。项目级 memory 是 scoped 的：基于某个项目的背景 + 以前讨论过的结论。触发词既能触发 skill，也能触发 memory 的读（回忆以前结论）和写（更新决策 log）。

维度 Task 目录 Skill
核心项目级 memory（背景 + 结论）可复用的确定性 SOP
生命周期一次性，任务完成归档长期，跨项目复用
触发触发词/清单（读 + 写）按名自动触发（SKILL.md 描述）

升级规则：某个脚本被多个 task / 项目复用 → 提升为正式 skill，不要积累重复逻辑。skill 目录本身也可以看作"跨项目稳定的 context"。
