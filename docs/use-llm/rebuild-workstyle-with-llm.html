为什么 LLM 会改变工作方式

当「造一个工具」的成本趋近于零，任何重复做两次以上的操作，都值得被工具化。这才是 LLM 对工作方式的真正改变。

过去搭一个工具是有成本的：要理解需求、写逻辑、处理边界、测试。所以人只肯把最高频、最痛的流程做成工具，剩下的都靠记忆和手工。而 LLM 把「造工具」这件事本身变成了一条低成本的流水线。

成本结构变了，决策就反转了：

  • 以前 「这个操作人肉做吧，写工具不划算」；现在 「让 AI 花几分钟生成一个 cli，以后都是确定性的」。
  • 以前工具是一次性的脚本，用完即弃；现在工具是可复用、可组合、可被再次编排的能力资产。
  • 人从「记住怎么做」转向「把做法沉淀成工具」，工作是沉淀出来的，而不是执行出来的。
核心论题：LLM 普及 → 工具成本趋近于零 → 「要不要做工具」的决策反转 → 工作方式的重造。

落到具体，这个「重造」有两个抓手，互为表里：

  • Build Tools：用 AI 大量生产原子化的命令行能力（可管道化、可单独跑）。
  • Build Workbench：把这些能力聚合、编排成一个统一入口（一个网页）。

Build Tools：用 AI 造可管子的能力

核心主张：用 AI 大量造命令行工具，采用 Unix 管道式设计。每个工具既是独立可运行的原子，也是 workbench 可编排的积木。

工具设计原则

  • 原子 & 单一职责：一个工具只做一件事，避免「什么都干」的重型脚本。
  • 管道式 I/O：读 stdin、写 stdout，可 A | B | C 自由组合。
  • 确定性优先：能用固定逻辑/程序实现的，别靠概率——显式指定能显著降低幻觉。
  • 独立可手动运行：脱离 workbench 也能在终端跑，作为兜底与调试入口。
  • 可读的错误反馈：报错要带细节（校验、堆栈、边界），让人和 AI 都能据此自我纠错。

具体到这个工作场景，先挑最容易量化的高频操作，比如：

  • publish：触发一次发布 / 发一条评论（类似现有 publish.py 的定位）。
  • override：做一次配置 / 特性覆盖。
  • query / graph：快速拉取上下文、画关系图。
关键的转变不是「用某个工具」，而是「批量生产工具」。给 AI 一套「工具生成模板 / SOP」，让造工具本身进入流水线——这是 harness 里「确定性 SOP」思路的延伸。

Build Workbench：all-in-one 聚合与编排

核心主张：把常用操作集成到一个网页，做成 all-in-one。它不做具体的事，而是做入口 + 编排。

为什么用 web 聚合：

  • 统一入口：发布、override、查询……都从一个地方触达，不用记一堆命令。
  • 可视化与低门槛：把 cli 的输入参数、返回结果变成表单和视图，人人可用。
  • 可编排：web 端可以串联多个 cli 工具，组成一个「操作流」。

dsh 类比 → 插件模式

类似 dsh 那样把高频操作集中在一个工具里；更进一步，把它拆成插件模式——每个能力登记成可插拔的 cli tool，随用随加。workbench 只负责调度，具体能力由插件提供。

workbench 与 tools 的关系：workbench 是编排者，tools 是被编排的原子；tools 也能脱离 workbench 手动运行。这样既保留「命令行原教旨」的灵活，又提供「一站式网页」的方便。

Workbench 分层架构

图：Workbench 分层架构，从上到下是前端、编排、可插拔 CLI 注册表，再下探到后端 / 外部系统；CLI 层也保留独立手动运行的通道。

解读：「前端」只做入口与展示；「编排层」是真正的中枢，负责参数校验、任务调度、把底层工具的返回变成可读反馈；「CLI 注册表」是能力层，即插即用；底层接 Java 后端与外部系统。图中右侧的虚线表示 CLI 也能脱离 workbench 在终端单独跑——这是刻意的冗余，保证工具永远可自助、可调试。

交互与设计考量

怎么跟不同工具交互

工具形态不同，交互契约也得统一：Java 后端走 HTTP / API，cli 走进程 / 管道。编排层需要一层适配，把各种调用变成统一的 「输入参数 → 执行 → 输出/错误」契约，否则调度逻辑会和具体工具耦合。

错误反馈是生命线

呼应 loop engineering：workbench 要能自我纠错，前提是工具把错误说得够细——校验失败原因、堆栈、边界情况，而不是一句「出错」。否则 AI / 用户都无从调整，闭环转不起来。

上下文与确定性

  • 能用确定性算法 / 固定逻辑的，别靠概率；显式指定能降低幻觉。
  • workbench 只注入「工具看不到的知识」，别重复塞模型能从环境里自己拿到的上下文——context 是稀缺资源。

workbench 与 tools 的角色分工

维度Build Tools（CLI）Build Workbench（Web）
定位原子能力，一件事只做一件事入口 + 编排，不做具体事
运行方式终端 / 管道，独立可跑网页，聚合可视
可复用性可组合成管道，可被再次编排按需接入能力插件
关键价值确定性的执行保障低门槛、一站式的使用体验

落地路径：从哪开始

  1. 先做最高频、最重复的 cli：发布、override、查询——那些「两周内会重复做>2 次」的操作，优先工具化。
  2. 搭一个最小 web 入口：先把这几个 cli 串成一个页面，验证「入口 + 编排」手感。
  3. 引入插件注册表 + 编排层 + 适配层：把工具登记成可插拔能力，统一调用契约。
  4. 沉淀工具生成模板 / SOP：让 AI 造工具这件事本身稳定下来，形成可复制的流水线。
一句话收束：让 LLM 把「做工具」变便宜，本质上是在把工作方式从「靠人执行」重造为「靠能力沉淀」。

附录：交互式工具打通

workbench 要编排的不只是「跑完即返回」的一次性 cli，还有交互式工具（需要多轮输入/输出来回）。打通它们的关键不是「该不该用终端仿真」，而是这个工具能不能被"结构化地驱动"。按这个能力，把工具分成三档：

三条路线：先分清工具能被怎么驱动

路线怎么驱动例子要不要 PTY
① SDK / RPC / JSON 模式工具暴露结构化程序化接口，web 渲染成聊天 / 卡片pi --mode rpc、pi SDK、git status --porcelain否
② 批处理 / 管道参数驱动、输出可解析、跑完即退出；web 拿 stdout 解析ls、grep、jq、curl、awk否（普通 spawn + pipe）
③ PTY + 终端仿真后端 PTY 起进程，浏览器 xterm.js 仿真终端，双向转发字节vim、htop、fzf、psql、REPL是

适配层怎么选

这不是「A 还是 B」二选一，而是适配层按每个工具动态选路：能批处理 / 管道化的 cli 走 ②（这正是「build tools 做成可管道化」的主线，本来就不需要 PTY）；有 SDK / RPC 的走 ①；剩下真正粘人的交互式工具才落 ③。所以 workbench 里绝大多数工具走 ② 就够了，A 是救生圈不是船。 ③ 把 web 变成「哑终端」——通用，但看不懂结构、做不了富交互；① 才让 web「理解」消息。

哪些工具「必须」用 PTY（③）

只有当工具需要真终端语义、且没有 ①②③ 之外可替代的路径时才必须——只要满足下面任意一条就走 ③：

  • 全屏 TUI：vim、htop、less、fzf——输出是「一屏画面」，没有实用的批处理模式，只能渲染终端。
  • REPL / 交互式 shell：bash、psql、mysql、redis-cli、ipython——历史、补全、多行编辑、提示符都靠 TTY。
  • 需要 /dev/tty 读秘密：getpass、sudo 密码、ssh -t——管道拿不到 /dev/tty，只有 PTY 行。
  • isatty() 才启用的行为：git 的 pager、只在 TTY 下才开颜色 / TUI。

但很多工具有折衷旗标，把「必须 PTY」的集合不断缩小：sudo -S、--password-stdin、--from-stdin、git -c core.pager=cat。真正躲不开 PTY 的，通常是它的核心价值就是那个交互终端本身（TUI/REPL），且作者没给非交互出口。

pi 的现成协议：pi --mode rpc

它在 stdin/stdout 上跑一个 JSONL 协议（每行一个 JSON），这就是「多轮输入/输出转发」的协议本体：

  • 发给 pi（stdin）：{"type":"prompt","message":"..."}，还有 steer、follow_up、abort、bash、new_session。
  • pi 推给你（stdout）：message_update（内含 text_delta/thinking_delta/toolcall_delta 流式增量）、turn_start/end、agent_settled、tool_execution_*、bash_execution_update。
  • 扩展 UI 子协议：工具要人确认时，pi 发 extension_ui_request（select/confirm/input/editor），你回 extension_ui_response——这就是「交互」那部分。

若后端是 Node，可直接用 SDK 的 createAgentSession() + session.subscribe() 在进程内跑，类型安全、状态可访问，更省事（见 docs/sdk.md）。

架构就一条

// server.mjs（Node，零 npm 依赖）
import { spawn } from "node:child_process";
import { createServer } from "node:http";
import { readFileSync } from "node:fs";

const pi = spawn("pi", ["--mode", "rpc", "--no-session"]);
const clients = new Set();

let buf = "";
pi.stdout.on("data", (chunk) => {               // pi 的 JSONL 事件
  buf += chunk;
  let i;
  while ((i = buf.indexOf("\n")) !== -1) {
    const line = buf.slice(0, i).replace(/\r$/, "");
    buf = buf.slice(i + 1);
    if (!line) continue;
    for (const res of clients) res.write(`data: ${line}\n\n`);   // 转成 SSE
  }
});

createServer((req, res) => {
  if (req.method === "GET" && req.url === "/") {
    res.setHeader("content-type", "text/html; charset=utf-8");
    return res.end(readFileSync("./index.html", "utf8"));
  }
  if (req.method === "GET" && req.url === "/events") {       // 输出通道
    res.writeHead(200, { "content-type": "text/event-stream", "cache-control": "no-cache", connection: "keep-alive" });
    clients.add(res);
    req.on("close", () => clients.delete(res));
    return;
  }
  if (req.method === "POST" && req.url === "/send") {        // 输入通道
    let body = "";
    req.on("data", (d) => (body += d));
    req.on("end", () => { pi.stdin.write(body.trimEnd() + "\n"); res.end("ok"); });
    return;
  }
  res.statusCode = 404; res.end();
}).listen(3000, () => console.log("http://localhost:3000"));

多轮 I/O 建模

你想做的对应做法
正常一轮对话{"type":"prompt","message":"..."}
agent 还在跑时插话prompt 带 "streamingBehavior":"steer"（或直接发 steer）
agent 跑完后的补充{"type":"follow_up","message":"..."}
打断当前操作{"type":"abort"}
工具要人确认收 extension_ui_request → 弹模态 → 回 extension_ui_response
刷新页面不丢上下文去掉 --no-session，或每会话一个 session 文件

坑与安全

  • 流式时再发 prompt 必须带 streamingBehavior，否则直接报错——新手最容易踩。
  • --no-session + 单进程 是单用户简化版；多会话/并发请每个连接 spawn 一个 pi，或用 SDK 每会话一个 AgentSession。
  • 安全：把能跑 shell 的 agent 暴露到 web，等于开了可执行任意命令的口子，务必鉴权/私有部署，别裸上公网。
  • 只有核心价值是交互终端（TUI/REPL）的才走 ③；pi 这类有结构化接口的走 ①，普通 cli 走 ② 更划算。
