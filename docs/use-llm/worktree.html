使用 AI 时的 Worktree 实践

标准形态只有一句话：主仓常驻 master，每个任务一个 worktree 目录，全部放在平级的 <repo>-wt/ 下。

~/workspace/
├──hello/master 主仓 · 只托管 .git，当 review 基准，不开 IDE
└──hello-wt/ worktree 容器，与主仓平级
├──xxx/feat/payment 任务 1 · 一个目录、一个分支、一个 IDE 窗口
└──yyy/fix/login 任务 2 · 和任务 1 同时推进

主仓里看得见的东西 + 表示这条分支不在这里

worktree 全部登记在主仓的 .git 里，所以在 hello 一个地方就能看全。别的 worktree 占着的分支，git branch 会在前面打 +；当前目录所在的分支是 *。

$ cd ~/workspace/hello
$ git worktree list
~/workspace/hello         8f3a1c2 [master]
~/workspace/hello-wt/xxx  4d9e07b [feat/payment]
~/workspace/hello-wt/yyy  1c77b20 [fix/login]

$ git branch
+ feat/payment
+ fix/login
* master

看到 + 就说明：这条分支正在 hello-wt/ 下的某个目录里被用着。想动它就去那个目录，或者干脆别在主仓里切——主仓只为 master 存在。

为什么：切分支突然变成成本

  • 人不再一次只做一件事。 有了 AI，人可以同时在两条分支上推进两个 feature：A 分支让 AI 跑测试，B 分支自己改设计。一个目录只有一个 working tree，只能靠频繁 git switch 硬扛。
  • 切分支会打碎 AI 的上下文。 AI 手里握着的是上一次读到的文件内容、目录结构、搜索结果、测试输出。你在它脚下换分支，这些缓存全部失真，模型却仍以为看到的是当前代码——幻觉就是这么来的。
  • 切分支也会打碎人的上下文。 编辑器 tab、构建产物、正在追的那条报错跟着一起换，每次都要重新热身。
  • review 需要一个稳定的对照物。 主仓停在 master 不动，每个 worktree 的 git diff master 就是这次任务的全部改动，干净可比。
两种做法对照
维度一个目录反复 git switch主仓 + 每任务一个 worktree
AI 上下文目录内容随时被换掉，缓存失真目录稳定，AI 读到的就是它正在改的
并行任务一次只能一个几个 worktree 同时跑
Review要记得自己在哪个分支上 diff主仓恒为 master，基准固定
代价无多几个目录、多几份 IDE 索引

一个 .git，三个工作区，一份远端

GitHub 上没有另一种东西——那个仓库同样是一个 .git，只是它不铺开成文件。下面三层，是同一个对象模型在三个位置的样子。

  • 工作区不存历史。它只是把对象库里某个 commit 的内容铺成文件。三个目录铺三份，所以能同时停在三个分支上。
  • objects/ 是全部历史，只有一份。blob 存文件内容、tree 存目录结构、commit 指向前两者。三个工作区共用它，所以 worktree 省空间。
  • refs/heads/ 是一张“分支名 → commit”的表，也只有一份。所以主仓里能列出全部分支，被 worktree 占着的那条前面打 +。
  • GitHub 上那份也是 .git，只是 bare：有 objects 和 refs，没工作区、没 index。push 就是把缺的对象传过去，再把远端 refs/heads/main 挪一格——所以没有“正本”，只有大家约定的 origin。

add 和 commit 到底写了哪些文件

一次 commit 的落点分在两处：对象和分支指针进了共享区，HEAD 与 index 留在这个 worktree 自己的区。

命令写进共享区 hello/.git/写进本 worktree
git addobjects/ 里新增 blob（内容新才新增）worktrees/xxx/index（暂存快照）
git commit新增 tree + commit；refs/heads/<branch> 指向新 commitworktrees/xxx/logs/HEAD；index 被刷新

两个反直觉的点：git add 就已经在写对象了，不是等 commit 才写——所以 add 完再丢弃改动，那个 blob 仍躺在 objects/ 里，等 gc 才回收。commit 也不改 HEAD，HEAD 只记“我在哪个分支上”，变的是那条分支的指针。

worktree 里一次 commit 的落点

# 共享：hello/.git/（全仓只有一份）
├── objects/0f2a…                新增 blob / tree / commit
├── refs/heads/feat/payment      挪到新 commit
└── logs/refs/heads/…            分支 reflog

# 这个 worktree 自己的：hello/.git/worktrees/xxx/
├── index                        只有这份被刷新
├── HEAD                         ref: refs/heads/feat/payment，没变
└── logs/HEAD                    本 worktree 的 reflog

主仓那个 master 一点没动：你 commit 的是 feat/payment，而且 master 正被主仓自己占着。自己验一下：

$ cd ~/workspace/hello-wt/xxx
$ cat .git                      # gitdir: .../hello/.git/worktrees/xxx
$ git commit -am "pay"
$ git rev-parse feat/payment    # 新 commit
$ cd ~/workspace/hello
$ git rev-parse master          # 完全没变
$ git log --oneline -1 feat/payment   # 主仓这边立刻能看到

git log 在主仓能看到别的 worktree 刚提交的东西，正是因为对象和 ref 都写在同一个 .git 里。这也是上一张图里「三个工作区指向上方同一个 .git」的实际含义。

唯一的交叉风险是共享区里的 ref：两个 worktree 同时 commit 不会冲突（各写各的分支 ref），同时 commit 到同一分支则根本不可能发生——git 一开始就不允许同一分支被两个 worktree 检出。

日常流程

  1. 先给 worktree 建个平级容器目录，一次性的事。 
    mkdir -p ~/workspace/hello-wt
  2. 开新任务：从主仓建 worktree。新分支用 -b，已有分支直接给名字。 
    cd ~/workspace/hello
git worktree add ../hello-wt/xxx -b feat/payment
git worktree add ../hello-wt/yyy fix/login
  3. 干活：在 hello-wt/xxx 里让 AI 改代码。主仓 hello 全程停在 master，一步不动；IDE 也从 worktree 目录打开。
  4. review：回主仓看这次任务的全部改动。三点语法 master...feat/payment 只显示这条分支引入的东西。 
    cd ~/workspace/hello
git diff master...feat/payment
  5. 合并、收工：先 merge，再删目录和分支。 
    git merge feat/payment
git worktree remove ../hello-wt/xxx
git branch -d feat/payment

IDE 从哪开

  • 打开 hello-wt/xxx，不是 hello。每个 worktree 是独立的 IDE 项目：独立的索引、独立的构建配置，.idea/ 就落在各自目录里。
  • 主仓 hello 不开 IDE。它只留在终端里当 git 和 diff 的基准。
  • 依赖不会重复下载。Maven 的 ~/.m2、Gradle 的 ~/.gradle 全局共享；多开 worktree 只多花 IDE 自己的索引空间，首次打开要等一次 index。
  • 几个窗口同时开时，注意同名文件。tab 上大多只显示文件名，几个 Application.java 分不清，把路径尾巴打开。
  • 先关 IDE 窗口，再 git worktree remove。反过来操作会在 IDE 里留一个指向空目录的 ghost project。

命令速查

命令作用
git worktree add <path> -b <branch>建目录 + 建分支，一步到位
git worktree add <path> <branch>把已有分支检出到新目录
git worktree list谁在哪个目录、停在什么 commit
git worktree remove <path>删除 worktree，有未提交改动会拒绝
git worktree prune清掉手工 rm -rf 后留下的登记残骸

注意事项

  • 同一个分支不能被两个 worktree 同时检出。git worktree add 会直接报 already checked out at ...。要并行跑同一份代码，用 --detach 或另开分支。
  • git worktree remove 不会替你保存现场。有未提交改动时它拒绝执行；确定要丢才加 --force，别把没合的东西一起删掉。
  • worktree 里的 .git 是一个文本文件。里面写着指向主仓 .git/worktrees/<name> 的路径。它不是一个独立仓库，别删、别拷走。
  • 主仓占着 master，AI 拿不到主干。要改主干就在 hello 里做——这正是主仓存在的意义。
  • 从 worktree 目录直接启动 AI 工具。让它看到的 pwd 就是真实位置；用 --work-tree 之类的参数把位置和目录拆开，会让 AI 对文件在哪产生困惑。
  • worktree 只隔离代码和 git 状态。数据库、端口、容器名、本地配置不隔离。几个 worktree 同时跑服务，要自己改端口和库名，否则互相打架。
  • 在 AGENTS.md / CLAUDE.md 里写明位置。一句"你在 worktree 中工作，主仓是 ~/workspace/hello"，AI 就不会跑回主仓改代码。
最关键的教训：不要图省事让 AI 在你的主目录上改代码。花十秒建一个 worktree，省的是后面几小时的上下文对不齐。
