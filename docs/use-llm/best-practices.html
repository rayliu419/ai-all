重新审视 Prompt Engineering

提示词的表达依然还是很有用。

  • grill skill：很短的提示词，效果很好（似乎在某些场景下尤其有效）。
  • AGENTS.md 里的 incident 标准模版，大幅提高了回答的层次性和合理性：
    • summary
    • root cause
    • chain
    • actions
  • 从这点来看，一些比较常见的任务，还是应该寻找好的 skills，这些 skills 会很大程度地改变 LLM 的回答质量。
    • 可以认为改变了 LLM 的思维方法和习惯。
  • 需要一个「阅读仓库」的 skill；自己随意写的还是效果不好。
    • 类似 GPT6，会给出很多无关细节的内容。
    • 好的阅读 skill 应能给出：
      • high level
      • concrete workflow

Memory：自动化生成与触发效果不好

自动化的 memory 生成和触发效果不好。

  • 替代方式：使用一个 docs-for-ai 文件夹，对某个可能偏长程的任务记录相关资料。
  • 目录结构暂时还不是很完美，需要迭代演进。
  • 在继续任务时，手动触发 LLM 阅读相关的文件夹资料。

积累 Domain 工具和知识库

  • example：couwatch = checkout 服务的 skill：查 log 用什么 label 过滤、查 metrics 用什么 label 查什么内容、不同故障的 SOP。
  • skill 结构：SKILL.md（工作流 + 导航）+ reference/（label 含义、SOP，按域拆分）+ scripts/（确定性脚本）。
couwatch/
├── SKILL.md        # 工作流 + 导航
├── reference/      # label 含义、SOP（按域拆分）
└── scripts/        # 确定性脚本（LLM 调用，只有输出进上下文）

脚本自动化降 cost

  • 原理：确定性操作用脚本，LLM 只调用 + 看输出，不重新生成代码。
  • 落地：手工重复 >1 次的操作 → 写成确定性脚本；脚本被多 task 复用 → 提升为 skill。
  • 约定：单文件、stdlib、CLI 长选项、TTY / 管道友好（见 CLI 工具约定）。

进入新领域三步：打通 → 说明 → 积累

打通（connect）

  • 用 MCP 把数据源 / tool 接进来；MCP = AI 的「USB-C 口」。
  • 三个 primitive：
    • tools —— 执行动作
    • resources —— 提供上下文数据
    • prompts —— 交互模板
  • 落地：本地优先 stdio server，远程用 streamable HTTP；接完只算「连得上」。

说明（explain）

  • 打通解决连通，还要告诉 AI「怎么用、何时用哪个」= ACI（agent-computer interface）。
  • 像写 docstring 一样写 tool：参数名 / 描述清晰、写明与其他 tool 的边界、给 example usage。
  • 衡量：人若无法判断该用哪个 tool，AI 更做不到 → 精简工具集、消除歧义。

ACI：好 / 坏 tool 描述对比（enrich）：

坏（模糊） 好（清晰）
描述「获取数据」「按 label 查 metrics；当需要看 checkout 的 QPS / 延迟 / 错误率时用」
参数datametric（指标名）、labels（过滤）、time_range（时间窗）
边界没写「查日志用 query_logs，别用这个」

积累（accumulate）

  • 逐步积累 skill / 知识库 + example 经验；触发以手动为主。
  • 用少数 canonical example（few-shot）而非穷举规则；edge case 用 "old patterns" 折叠，不塞主路径。
  • 反馈闭环：validator → 改 → 再验，写进 skill 的 workflow。

按任务强度路由模型

模型已分化：贵的模型慢且贵，不适合 incident 或要求响应快的需求。所以要人为判断任务强度，综合使用（而非一个模型打天下）：

  • 强模型（gpt6 / opus5.5 max 等，极贵）→ 复杂问题分析、设计。
  • flash 类模型 → 执行（直接写代码），快且便宜。

一个任务可以组合：强模型出方案 / 设计 → flash 执行。

模型路由决策表（enrich）：

任务强度 用什么模型 典型场景
复杂分析 / 设计gpt6 / opus5.5 max 等（极贵、慢）架构设计、复杂问题分析
执行flash 类（快、便宜）直接写代码、incident 快速响应

Hard rule：用代码而不是 prompt 约束

能被确定性判定的约束，就不该写在 prompt 里 —— 写成代码。

  • 软约束（prompt）：靠模型每次自觉遵守，会漂移、会被上下文稀释。
  • 硬约束（代码）：执行路径唯一、可验证、可回归。

对照表：

写在 prompt 里的“约束” 应该落到代码
“提交信息要符合 conventional commits”commit-msg hook / commitlint
“命名和风格要统一”lint rule（不写进 AGENTS.md）
“不要改 public API 签名”测试 + CI 直接卡住
“每次改完记得跑测试”stop hook / 脚本自动跑
“输出必须是合法 JSON”function / tool schema + validator

分工：prompt 管意图、取舍、上下文；代码管必须成立的事实。

  • 收益：省 token、减少来回纠正、约束不随上下文增长而衰减。
  • 例外：不可判定的（风格偏好、权衡取舍）只能留在 prompt / skill，别硬编码。
