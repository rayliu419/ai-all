把一次性经验沉淀为可复用资产（skill / 脚本 / 知识库）。
真正的难点不在"能不能用 LLM"，而在"怎么让经验跨 session 复用、怎么控制成本"。

核心主张

上下文是有限注意力预算：token 越多，模型精确回忆越差（context rot）。所以主线是渐进式披露——只放当前需要的高信号 token，其余按需加载。

渐进式披露的三层加载（skill 是这套机制的标准载体）：

L1 元数据   → 常驻上下文（每个 skill 约 ~100 token，可装几十个）
L2 指令     → 触发时才读（SKILL.md 正文）
L3 资源/脚本 → 需要时才读/执行（脚本代码不进上下文，只有输出消耗 token）

三种资产，用三种不同的机制承载：

资产 内容 触发 / 加载机制
程序性知识怎么做（流程、SOP）skill 的 description 匹配任务模式
情景记忆之前讨论 / 决定了什么系统提示词提示 + LLM 决策搜索
领域知识label 含义、schema、SOP装进 skill 的 reference，按需读

两个真难点——memory 的触发、积累的触发——都不靠自动规则：前者靠"提示 + LLM 判断"，后者靠"手动"。

Memory：提示 + LLM 决策搜索

memory 真正的难点是何时触发什么：你不知道历史里有没有相关内容，直到去查。所以它不适合做成 skill——skill 的 description 匹配的是"任务模式"（如"查 log"），匹配不了"有没有相关历史"这种模糊触发。

方案：在系统提示词里给一句提示，让 LLM 自己决定何时去本地搜：

tasks-for-ai/ 记录了我们讨论过的问题，有时可以去搜索一下有没有背景，尤其是 session 刚开始时。

探索决策流程：

开始一个任务
      │
      ▼
  系统提示词里有句提示：
  "tasks-for-ai/ 记录过讨论过的问题，有时可搜背景"
      │
      ▼
  LLM 自行判断：需要搜历史吗？
   ├─ 否 ────────────────────▶ 直接动手
   └─ 是
        │
        ▼
  本地 grep 关键词
   ├─ 无命中 ────────────────▶ 直接动手
   └─ 命中
        │
        ▼
  读 background.md / decision log
        │
        ▼
  带着结论继续
  • 本质是本地 keyword 搜索（grep）：便宜，命中才读详情。
  • 时机建议：session 刚开始优先 + 过几步再探索一下，是否搜由 LLM 决策。
  • 索引一行一个主题（便宜扫）；命中才读 background.md / decision log（按需）→ 这就是渐进式披露用在 memory 上：index（便宜）→ note（按需）。
  • 兜底：用户显式说"继续 X / 回忆 X"也是可靠触发。

Domain 工具与知识库

目标：查问题 / 做任务不用反复说背景。核心在逐步积累。

自动积累很难触发准确——因为"值不值得记"是判断（可复用结论 vs 一次性流水账），模型没信号时判不准。所以手动为主，把"写"这一步做到零摩擦。

  • 触发信号：用户显式（"记录 / 沉淀 / 记住"）+ 固定时点（每 ~5 轮、/compact 前、session 结束前）。
  • 写路径预先定好，手动成本低：append 到 decision log，或加到 domain skill 的 reference。
  • 引用只保持一层深（SKILL.md 直接链 reference，避免嵌套导致模型 head 半读）；按 domain 拆文件避免加载无关上下文。

例子：couwatch skill（checkout 服务）

它封装了查 log / metrics 的一揽子知识：log 用什么 label 过滤、metrics 用什么 label 查什么内容、不同故障的 SOP。

couwatch/
├── SKILL.md                # 工作流 + 导航：如何排查 checkout 故障
├── reference/
│   ├── logs.md             # log 查询：哪些 label 过滤、各 label 含义
│   ├── metrics.md          # metrics 查询：哪些 label 查什么指标
│   └── sop/
│       ├── payment-timeout.md   # 支付超时 SOP
│       ├── high-latency.md      # 高延迟 SOP
│       └── ...
└── scripts/
    └── query_logs.sh       # 确定性脚本（LLM 调用，只有输出进上下文）

reference/ 里的 label → 含义映射（示意，真实内容按服务实际标签填）：

类型 label 含义
logservice=checkout过滤 checkout 服务的日志
loglevel=error只看 error 级日志
metricsendpoint=/pay支付接口的指标
metricsstatus=5xx服务端错误相关指标

脚本自动化降 cost

原理：确定性操作用脚本，LLM 只调用 + 看输出，不重新生成代码。

让 LLM 现场写代码：代码 + 输出都进上下文（贵，且易错）。
调用现成脚本：只有 stdout 进上下文（省，且确定）。

  • 落地：手工重复 >1 次的操作 → 写成确定性脚本；脚本被多 task 复用 → 提升为 skill。
  • 约定：单文件、stdlib、CLI 长选项、TTY / 管道友好（| head 不报错、非 TTY 只输出可读列表）。

新领域三步：打通 → 说明 → 积累

4.1 打通（connect）

用 MCP 把数据源 / tool 接进来；MCP = AI 的"USB-C 口"。三个 primitive：

primitive 作用
tools执行动作（查库、调 API）
resources提供上下文数据（schema、文档）
prompts交互模板（few-shot 示例）

落地：本地优先 stdio server，远程用 streamable HTTP；接完只算"连得上"。

4.2 说明（explain）

打通只解决连通，还要告诉 AI"怎么用、何时用哪个"——即 ACI（agent-computer interface）。像写 docstring 一样写 tool：

坏（模糊） 好（清晰）
描述"获取数据""按 label 查 metrics；当需要看 checkout 的 QPS / 延迟 / 错误率时用"
参数datametric（指标名）、labels（过滤）、time_range（时间窗）
边界没写"查日志用 query_logs，别用这个"

衡量标准：如果人都无法判断该用哪个 tool，AI 更做不到 → 精简工具集、消除歧义。

4.3 积累（accumulate）

  • 逐步积累 skill / 知识库 + example 经验；触发以手动为主（见 Domain 工具与知识库）。
  • 用少数 canonical example（few-shot）而非穷举规则；edge case 用 "old patterns" 折叠，不塞主路径。
  • 反馈闭环：validator → 改 → 再验，写进 skill 的 workflow。

按任务强度路由模型

模型已分化：贵的模型慢且贵，不适合 incident 或要求响应快的需求。所以人为判断任务强度，综合使用（而非一个模型打天下）：

任务强度 用什么模型 典型场景
复杂分析 / 设计gpt6 / opus5.5 max 等（极贵、慢）架构设计、复杂问题分析
执行flash 类（快、便宜）直接写代码、incident 快速响应

一个任务可以组合：强模型出方案 / 设计 → flash 执行。
