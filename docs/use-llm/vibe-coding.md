## goal
- vibe coding 的效率来自「改形状几乎免费」，而不是「AI 会写码」。
- 所以正确用法：**写实现之前，先用 AI 把六个形状迭代到稳定**，之后让实现去 conform。
- 这六步的产出都是**可 diff 的文件**，不是「在对话里说清楚了」。

## 六步骨架（顺序即成本序）

| 步 | 产出物 | 固定住什么 | 为什么贵 |
| --- | --- | --- | --- |
| ① mockup | `mockup.html` | 界面、信息密度、交互路径 | 界面一改，数据与接口跟着改 |
| ② DB 设计 | `schema.sql` + 关键查询 | 实体、关系、时间维度 | 最难改，历史数据要迁移 |
| ③ 流程图 | `flow.mmd` | 时序、状态、失败分支 | 流程漏一步，实现漏一片 |
| ④ 命名 | `glossary.md` | 领域词汇（名词 + 动词） | 命名漂移会传染整个代码库 |
| ⑤ 目录结构 | `tree` | 模块边界 | 边界错了，后面全靠 import 打补丁 |
| ⑥ 系统层次 | `layers.md` | 依赖方向 | 层次乱了，改一处动全身 |

顺序的依据：**从「人一眼能判断对错」到「只能靠推演判断」**。mockup 谁都看得出不对，分层只有写完才知道对不对——所以越靠前越该多迭代。

## 每一步怎么做

### ① 让 AI 出 mockup
- 要一个**能点的 HTML**（不是 Figma 稿、不是文字描述）。三屏以内，只画主流程。
- 提示要点：说明这是哪个系统的哪个页面、有哪些区域、每张卡片上有什么信息、有哪些按钮。
- 验收：不用解释就能看懂主流程；不看代码就知道点哪里会发生什么。

### ② 让 AI 做 DB 设计
- **先给「要回答的问题」，不要先给表**。让 AI 从问题反推实体与关系。
- 要求：每个页面上的每个字段都能追到来源；**状态变化单独建模**（时间维度），不要用字段覆盖历史。
- 验收：随便挑一个界面元素，能说出它来自哪张表哪条记录。

### ③ 让 AI 出流程图
- 要 mermaid，一屏看完；必须画失败分支和「人需要确认」的节点。
- 验收：每个「人会犹豫怎么办」的地方，图上都有分支。

### ④ 让 AI 做好函数命名
- 先定 **10 个核心名词 + 5 个核心动词**，写进 glossary；禁止同义词。
- 函数名 = 动词 + 名词（`refreshPermissions` / `scanJiraDaily`），不用 `handleXxx`、`processXxx`。
- 验收：代码里出现第二个同义词（如既有 `ticket` 又有 `issue`）= 词汇表没定好。

### ⑤ 定好开始的目录结构
- 按「**变化的原因**」分（feature-first），不按技术层分（不是 `controllers/ services/`）。
- 一个插件 / 一个功能一个目录，目录里自带它的数据源、任务、UI。
- 验收：改一个功能只动一个目录。

### ⑥ 定好系统的层次
- 写死依赖方向（如 UI → domain → data，禁止反向），并写进 AGENTS.md。
- 验收：能用一句话说出每层职责；能让 AI 判断「这段代码该放哪一层」。

## 为什么这六步有效

- **顺序**：从具体到抽象，从便宜到昂贵。
- **落盘**：每一步都有文件，AI 每次都能 conform，新 session 也不会重来。
- **可评审**：形状比实现容易 review，错在形状阶段改，成本是写码的百分之一。

## 反模式

- 先写实现，再补 mockup（形状被实现绑架）。
- 让 AI 一次出整套设计（六步混在一起，无法逐个 review）。
- 形状只活在对话里（下个 session 就丢，等于没定）。
- 命名与目录交给 AI 自由发挥（词汇与边界会漂移）。

## 与其他笔记的关系

- `harness.md`：怎么让模型稳定输出（模板 / skill / context）。
- `best-practices.md`：日常使用技巧（skill 化、脚本降本、memory）。
- `one-workbench.md`：这套手法的实践出处（插件 manifest、run 记录、分层都是先定形状再填内容）。
