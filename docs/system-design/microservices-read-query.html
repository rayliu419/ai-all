微服务中的 Read Query 处理

微服务架构采用"Database per Service"模式，join 跨多个服务的数据成为一个核心难题。本文首先讨论跨服务数据聚合的三种核心方案：API Composer、CQRS + Materialized View、Event Sourcing；然后单独讨论这些方案引入的一致性问题（Read-Your-Writes）和批量查询性能优化这两个跨切面专题。

核心矛盾：微服务要求数据按服务边界独立存储（Database per Service），但业务查询往往需要跨越多个服务的数据。解决方案的实质是在 耦合度、一致性、查询性能 之间做权衡。

1. 问题背景

微服务读请求面临的核心问题可以归纳为三类：

  • 跨服务数据聚合：join 的数据分散在不同服务的数据库中，无法用传统 SQL join。这是本文方案一~三要解决的核心问题。
  • 数据一致性：异步聚合方案（CQRS、Event Sourcing）引入最终一致性，用户刚写入的数据可能读不到。这是第5节 RYW 要解决的问题。
  • 批量查询性能：即使在同一服务内，按低基数字段（如 status）批量过滤时 MySQL 索引效率低，需要专门的优化策略。这是第6节要讨论的问题。
一个常见的误解：CQRS 就是读写分离。实际上"读写分离"通常指读写用同一类 DB（如 MySQL 主从），而 CQRS 允许用完全不同的 DB 类型来满足查询需求 —— ES 做搜索、MongoDB 做文档聚合、Neo4j 做图查询。

2. 方案一：API Composer 跨服务聚合

解决什么问题

实时跨服务数据聚合——客户端需要同时获取 Service A、B、C 的数据并组合在一起时，如何在不改变现有服务的前提下完成 join。

原理

引入一个 API Composer（通常是 API Gateway 或独立的组合服务），分别调用多个微服务的 API，在内存中完成 join 后返回。

data_a] GW --> SB[Service B
data_b] GW --> SC[Service C
data_c] SA --> J{In-memory Join} SB --> J SC --> J J --> R[Response] style C fill:#e3f2fd,stroke:#2196f3 style GW fill:#e8f5ec,stroke:#4caf50,font-weight:bold style J fill:#fff3e0,stroke:#ff9800

优缺点

优点缺点
实现简单，不改变现有服务多次网络交互增大延迟
无需额外存储降低可用性 (A × B × C)
适用于数据量小的场景大数据集 in-memory join 低效
数据实时性最好数据不一致（各服务返回时刻不同）

引入的问题与缓解措施

问题 1：可用性降低——依赖的服务越多，整体可用性越低。

  • 并行调用：缩短延迟窗口，可用性取决于最慢/最不可用的单一服务而非乘积。
  • 熔断降级：某个服务超时/失败时，返回部分数据而非整体失败。
  • 缓存兜底：对非实时敏感的数据加本地缓存，减少实时依赖。

问题 2：多源数据不一致——各服务返回的是不同时刻的快照，组合后逻辑上可能矛盾（如订单状态为"已发货"但配送记录还没生成）。

  • 接受弱一致：在非关键场景下接受最终一致性。
  • 关键数据走主库：对一致性要求高的字段，直接从所属服务的主库读取。
可用性计算示例

假设 Service A、B、C 各自可用性为 99.9%（3 nines），API Composer 串行调用它们：

整体可用性 = 0.999 × 0.999 × 0.999 = 99.7%

这意味着每年的停机时间从 8.76 小时（单个服务）增加到 26.3 小时（组合后）。如果改为并行调用，可用性取决于最小可用性，但延迟取决于最慢的服务。

适用场景

  • 数据量小（翻页、聚合结果数可控）
  • 实时性要求高
  • 简单的主数据聚合（如查用户 + 查订单）
  • 不适合大数据过滤、复杂聚合查询

3. 方案二：CQRS + Materialized View 跨服务聚合

解决什么问题

高性能跨服务复杂查询——当 API Composer 无法满足性能要求（大数据量 join 低效、频繁跨服务调用延迟高），或者查询模式复杂（多条件过滤、全文搜索、图查询）时，需要将数据预聚合到专为查询优化的存储中。

核心思想

CQRS (Command Query Responsibility Segregation) 将命令（写操作）和查询（读操作）分离到不同的模型中，甚至使用完全不同的存储。

Command 侧
负责数据变更。使用业务模型，写入自己的 DB。关注数据完整性、验证逻辑、事务边界。
Query 侧
专门为查询优化。使用不同的 DB 类型、不同的 schema、不同的索引策略。可存在多个 View DB。

Materialized View 的角色

Materialized View（物化视图）是 CQRS 中 Read Model 的具体实现方式。它在多个数据源之上预先建立只读的、已聚合的视图。视图是完全可丢弃的——可以从源数据完整重建。Command 侧写入 → 事件驱动更新 Materialized View → Query 侧读取 Materialized View。

架构

ElasticSearch] EH2 --> VDB2[View DB
MongoDB] EH3 --> VDB3[View DB
Neo4j] subgraph Query["Query Side"] VDB1 VDB2 VDB3 end style Command fill:#e8f5ec,stroke:#4caf50 style Query fill:#e3f2fd,stroke:#2196f3

每个服务发布领域事件（Domain Events），Query 侧监听这些事件，构建和维护自己的 View DB。

典型例子：Order History Service

来自 Chris Richardson Microservices Patterns 中的经典案例 findHistoryOrder：

  1. Order Service 发布 OrderCreated、OrderShipped 等事件。
  2. Kitchen Service、Delivery Service、Accounting Service 各自发布领域事件。
  3. Order History Service 监听所有相关事件，在 View DB 中融合数据。
  4. View DB 使用文档数据库，schema 按查询需求设计（反范式化，无需 join）。
关键洞察："数据的拥有者（设计数据模型的微服务、修改数据实体的微服务），不一定由它来实现所有的查询。"——数据的写入边界和读取边界可以是不同的。Order History Service 不"拥有"订单数据，但它可以维护一个专为历史订单查询优化的 View DB。

优缺点

优点缺点
查询性能高，schema 按需优化架构复杂度大幅增加
读写独立扩展需要维护事件同步机制
可混合使用多种 DB最终一致性，有复制延迟
Command 侧业务逻辑更简洁代码一定程度重复

引入的问题与缓解措施

问题：最终一致性——这是 CQRS 最核心的代价。Command 侧写入成功后，View DB 的同步存在延迟。用户可能看到过时数据，甚至完全看不到自己刚写入的数据（read-after-write inconsistency）。

  • UI 提示：告诉用户"数据已收到，将在数秒内更新"。降低用户对实时性的预期。
  • 乐观 UI：写成功后立即在本地更新展示，不等后端确认。
  • Read-Your-Writes (RYW)：对刚修改过的数据，保证用户能立即读到一致的结果。详见第5节。
  • 监控延迟：跟踪 View DB 与 Command DB 之间的同步延迟，超出阈值时告警。
注意：RYW 不是 CQRS 的必选项，而是在"用户体验"和"架构简洁性"之间的一个权衡点。是否需要 RYW、选择哪种 RYW 策略，主要看用户的失望成本有多高。

Materialized View 应用场景

  • 多表 join 的复杂查询预计算
  • 报表、大屏、统计场景
  • 微服务场景下跨服务数据聚合
  • 存储异构数据（关系型 + 文档 + 全文索引）

4. 方案三：Event Sourcing 跨服务聚合

解决什么问题

审计追踪与时态查询——当系统需要记录所有历史变更、支持"一个月前的订单状态是什么？"这种查询、或者需要基于事件的跨服务协作时，传统的 CRUD 模式无法满足。Event Sourcing 提供了一条不同的数据存储路径。

原理

不存储当前状态，而是存储所有变更事件（append-only log）。当前状态通过重放所有事件来计算（rehydration）。

审慎采用：Event Sourcing 复杂度极高。仅在需要审计追踪、时态查询、事件驱动协作的场景下使用。对于大多数系统，传统 CRUD + CQRS 已足够。

与 CQRS 的协同

  • Command 侧：append 事件到 Event Store（命令校验后生成事件）。
  • Query 侧：监听事件，构建 Materialized View。
  • Event Store：作为单一真相源（System of Record），提供完整的审计追踪。

CQRS + Event Sourcing 架构

优缺点

优点缺点
完整的审计追踪极高复杂度，学习曲线陡峭
支持时态查询（任意时间点的状态）事件版本演进困难
天然支持事件驱动协作Rehydration 性能可能成为瓶颈
Event Store 是可靠的真相源需要快照机制优化重放性能

引入的问题与缓解措施

问题 1：事件版本演进——事件结构随业务需求变化，旧事件和新代码可能不兼容。

  • 向上兼容：新增字段设默认值，不下线旧字段。
  • 事件版本号：在事件中显式记录 schema 版本，处理器按版本路由。
  • 事件转换器：在读取时对旧版本事件做原地或 on-the-fly 转换。

问题 2：Rehydration 性能——从头重放全部事件恢复状态，事件量越大越慢。

  • 快照（Snapshot）：每隔 N 个事件记录一个状态快照，重放时从最近快照开始。
  • 异步 Materialized View：查询不从 Event Store 重放，而是从 View DB 读取。

适用场景

  • 需要审计追踪（如金融交易、合规系统）
  • 需要时态查询（如"查看历史任意时刻的账户余额"）
  • 事件驱动协作（多个服务需要响应同一组事件）
  • 不适合简单 CRUD 系统
跨切面说明：以下两节讨论的不是与方案一~三平行的"方案"，而是这些方案（特别是 CQRS）引入的衍生问题及其解决方法。它们是水平跨切面，在评估架构时需要一并考虑。

5. 一致性专题：Read-Your-Writes

这个专题讨论什么

前文方案二（CQRS）的核心代价是最终一致性：Command 侧写入后，View DB 的同步存在延迟。这导致用户刚写入的数据在查询时读不到——即 read-after-write inconsistency。RYW（Read-Your-Writes）保证用户对自己写入的数据能立即读到一致的结果。

注意：这不是跨服务查询的"第五种方案"，而是方案二引入的问题的解决策略。

问题场景

%%{init: {'theme': 'base', 'themeVariables': { 'actorMargin': '12' }}}%% sequenceDiagram actor User participant Command as "Command Side" participant Query as "Query Side" User->>Command: POST /orders Command-->>User: 201 OK User->>Query: GET /orders/123 Query-->>User: 404 Not Found Note right of User: 用户看不到刚写入的数据
View DB 尚未同步

本质矛盾：Command 侧写成功了，但 Query 侧还没来得及同步，用户看到"数据丢了"或"操作没生效"。

策略 A：Write-Through（同步刷新）

写入 Command 侧后，同步等待 View DB 更新完成再返回响应。

%%{init: {'theme': 'base', 'themeVariables': { 'actorMargin': '12' }}}%% sequenceDiagram actor User participant Command as "Command Side" participant Query as "Query Side" User->>Command: POST /orders Command->>Query: 同步写入 View DB Query-->>Command: 确认 Command-->>User: 201 OK User->>Query: GET /orders/123 Query-->>User: 200 OK (数据已存在)
优点缺点
逻辑简单，立即可见写延迟增大（需等待所有 View DB）
对客户端透明写可用性降低（依赖 View DB）

适用：需要严格 RYW、写频率不高的场景。

策略 B：Read-Your-Writes Session

为每个用户会话维护一个版本号或时间戳。

  1. 写操作返回一个写入时间戳或 event ID。
  2. 读请求携带该时间戳，Query 侧在同步未追平时阻塞等待或返回特殊状态。
  3. 或由客户端等待一段时间后重试。
%%{init: {'theme': 'base', 'themeVariables': { 'actorMargin': '12' }}}%% sequenceDiagram actor User participant Command as "Command Side" participant Query as "Query Side" User->>Command: POST /orders Command-->>User: { orderId: 123, version: 42 } User->>Query: GET /orders/123?after_version=42 alt 已同步 Query-->>User: 200 OK 数据已返回 else 未同步 Query-->>User: 425 Too Early 请稍后重试 end

策略 C：Read from Command Side（直接读主库）

对于用户刚写入的数据，直接从 Command 侧（主库）读取。适用于用户的"我的订单"等个人数据查询。

优点缺点
强一致性增加 Command 侧读负载
无需同步机制通常 Command 侧不是为读优化的

策略 D：Logical Replication with Monotonic Reads

利用数据库自身的复制机制（如 MySQL binlog、Kafka 分区），保证同一 partition key 的读写按顺序到达。

  • 单用户的所有请求路由到同一 partition。
  • Partition 内事件严格有序，读操作在写操作之后到达该 partition 的 View DB。
  • 天然保证该用户的 RYW。

策略选择

策略一致性写延迟复杂度适用
Write-Through强升高低低频写，严格 RYW
RYW Session最终 + RYW不影响中大部分 CQRS 场景
Read from Command强不影响低个人数据查询
Monotonic Reads最终 + RYW不影响高高吞吐 CQRS
关键原则：优先保证用户在自己的数据上看到强一致性（RYW），对其他用户的数据可以接受最终一致。

6. 性能专题：批量查询与索引优化

这个专题讨论什么

前面方案一~三关注的是跨服务的数据聚合。但即使在单个服务内部，也面临批量查询性能问题——特别是按低基数字段（如 status）做过滤时，MySQL 索引效率很低。本节讨论的优化策略适用于单服务或跨服务中的读性能提升。

来自笔记中的实际场景：

场景 1：按 status 批量查询

CORS 大数据管理面需要批量查失败/未调度的记录；GIM Migration 需查很久未完成的任务。

优化策略（从简单到复杂）：

方案说明成本
避免直接查 status用创建时间作为索引字段，批量查询后读 status 再过滤低
status 单独建表拆成标志位表/压缩表，扫描行数少低
复合索引(status, create_time) 联合索引，减少回表低
CQRS + ES用 ES 存储待过滤的记录，过滤效率极高中高

场景 2：DJS 查询下一分钟调度的记录

方案：在任务执行时，同时生成下次执行的时间戳，将时间戳作为 hash key，快速定位一批记录。这是典型的"调度时间预计算 + 精确索引"策略。

通用索引设计原则

  • 查询需求驱动：确定哪些是常见查询，为它们创建索引。
  • 列选择：为 WHERE、JOIN、ORDER BY 中频繁使用的列建索引。
  • 复合索引：多列查询条件考虑联合索引，最左前缀原则。
  • 索引覆盖：尽量让索引包含查询所需的所有列，避免回表。
  • 维护成本：不过度创建索引。DELETE/UPDATE 的性能会受影响。
  • 监控优化：使用 explain / 慢查询日志持续优化。

低基数字段（如 status、type、flag）的值种类很少（比如 status 只有 4~20 种取值）。B+树索引可以用二分查找快速定位到一个 status 值在索引中的位置，但是——找到之后发现这个值对应的行数可能占总表的 25%（如果有 4 种 status），仍然需要扫描大量行。而且这些行分散在磁盘上，每回表一次就是一次随机 I/O。所以问题的本质不是"查不到"，而是"查到的数据太多 + 回表成本太高"。

以下是针对性的优化手段：

方法 1：覆盖索引（Covering Index）—— 消除回表成本

如果索引本身包含了查询需要的 所有列，MySQL 就不需要回表去读数据行了。即使索引扫描了 25% 的行，那也是在 B+树上的顺序扫描，比随机 I/O 快得多。

-- 业务需求：按 status 查订单的 id、status、create_time
-- 原 SQL（会回表读数据行）：
SELECT id, status, create_time FROM orders WHERE status = 'FAILED';

-- 建覆盖索引：
CREATE INDEX idx_status_created ON orders(status, create_time);
-- 现在索引 (status, create_time) 包含了所有查询列，EXPLAIN 会显示 Using index（不需要回表）
适用条件：查询列固定且较少。如果 SELECT * 或者列很多，覆盖索引会变得过大，维护成本高。

方法 2：Index Skip Scan —— 让优化器帮你"拆查询"

复合索引 (status, create_time) 在查询 WHERE status = 'FAILED' 时，按理说只能用到 status 部分，create_time 用不上。但 MySQL 8.0.13+ 的 Index Skip Scan 可以绕过这个限制：

-- 有索引 (status, create_time)，但只想按 status 查
EXPLAIN SELECT * FROM orders WHERE status = 'FAILED';
-- 如果 status 有 4 个 distinct 值，MySQL 会隐式地把它拆成：
--   (SELECT * FROM orders WHERE status = 'FAILED' AND create_time >= MIN)
--   UNION
--   (SELECT * FROM orders WHERE status = 'FAILED' AND create_time BETWEEN ...)
--   ...

-- 等价于手动做：
SELECT * FROM orders WHERE status = 'FAILED' AND create_time > '1970-01-01';
-- 但 MySQL 自动帮你完成了这个"跳过"逻辑

效果：即使 status 选择性低，Index Skip Scan 也能利用完整的复合索引做 range scan，比全表扫描快得多。

关键限制：status 的 distinct 值越少效果越好（5~20 个）。如果 status 有 1000 种取值，Skip Scan 就需要遍历 1000 次，反而更慢。

方法 3：分区表（Partitioning）—— 物理隔离数据

按 status 分区后，每个分区只存一种 status 的数据。查询 WHERE status = 'FAILED' 时，MySQL 通过"分区裁剪"（Partition Pruning）直接跳过无关分区，只扫一个分区。

CREATE TABLE orders (
  id BIGINT NOT NULL,
  status ENUM('PENDING','PROCESSING','SUCCESS','FAILED') NOT NULL,
  create_time DATETIME NOT NULL,
  data TEXT,
  PRIMARY KEY (id, status)   -- 分区键必须是主键的一部分
) PARTITION BY LIST COLUMNS(status) (
  PARTITION p_pending VALUES IN ('PENDING'),
  PARTITION p_processing VALUES IN ('PROCESSING'),
  PARTITION p_success VALUES IN ('SUCCESS'),
  PARTITION p_failed VALUES IN ('FAILED')
);

-- 查询现在只扫 p_failed 分区
EXPLAIN SELECT * FROM orders WHERE status = 'FAILED';
-- partitions 列显示：p_failed（其他分区被裁剪掉了）

分区表的本质是用物理文件隔离替代索引过滤。缺点：分区数不宜过多（建议 < 50），且 status 值变化时需要 ALTER TABLE 调整分区。

方法 4：INDEX_MERGE（位图合并）—— 用多条小路拼出大路

当查询涉及多个低基数字段时（如 WHERE status = 'FAILED' AND type = 3），单一索引效率很低。但 MySQL 5.6+ 可以分别用两个索引查出各自的"位图"，然后做交集：

-- 两个单列索引
CREATE INDEX idx_status ON orders(status);
CREATE INDEX idx_type ON orders(type);

-- 查询
EXPLAIN SELECT * FROM orders WHERE status = 'FAILED' AND type = 3;
-- Extra 列会显示：Using intersect(idx_status, idx_type)
-- 执行过程：
--   1. 用 idx_status 找到所有 status='FAILED' 的行（得到一个 rowid 集合 A）
--   2. 用 idx_type 找到所有 type=3 的行（得到 rowid 集合 B）
--   3. 对 A 和 B 做交集，只回表读交集部分的 10 行

如果没有 INDEX_MERGE，MySQL 只能选择其中一个索引（扫 1000 行）或全表扫。INDEX_MERGE 把两个 10% 的数据集交成了 1%，大幅减少回表次数。

注意：INDEX_MERGE 不是万能的——优化器只在它认为合并比全表扫/单一索引更优时才会启用。可以用 FORCE INDEX(idx_status, idx_type) 或 IGNORE INDEX 测试是否生效。

方法 5：单独状态表（Thin Status Table）—— 把数据切薄

如果主表行很大（比如 data TEXT/BLOB 列占几 KB），B+树扫描时每读一行 I/O 成本很高。把 (id, status) 拆成一张极薄的表，每行只有十几个字节，一个数据页能装几百行，全表扫描也很快。

-- 主表（行很大）
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  status VARCHAR(20),
  data LONGTEXT,          -- 几 KB
  ...
);

-- 状态表（极薄，每行约 10 bytes）
CREATE TABLE order_status (
  id BIGINT PRIMARY KEY,
  status VARCHAR(20),
  INDEX idx_status(status)
);

-- 查询：只扫薄表
SELECT id FROM order_status WHERE status = 'FAILED';
-- 一行一个数据页可能包含 500+ 条记录，扫描 100 万行也很快

-- 拿到 id 后，可以再 INNER JOIN 主表只取需要的行
SELECT o.* FROM order_status s
JOIN orders o ON o.id = s.id
WHERE s.status = 'FAILED';

本质上是对数据做了"列裁剪"——只把用于过滤的列放到小表中，让每次 I/O 读到更多行。

总结：低基数字段没有银弹。覆盖索引消除回表成本（最简单有效）、Index Skip Scan 利用复合索引做 range scan（8.0+ 专享）、分区表物理隔离数据（适合稳定状态集）、INDEX_MERGE 用多个窄索引做交/并运算（适合多条件过滤）、单独状态表把数据切薄（适合宽表场景）。在实际优化时，先用 EXPLAIN 确认瓶颈是"扫了太多行"还是"回表太贵"，然后选择对应的方法。

混合使用建议

  • 简单查询：API Composer 足够。不需要引入 CQRS 复杂度。
  • 核心查询路径：CQRS + Materialized View。View DB 按需选择（文档 DB / ES / 图 DB）。
  • 批量/后台任务：索引优化 + CQRS。避免直接查低基数字段。
  • 复杂业务 + 审计需求：Event Sourcing + CQRS。但限定在有收益的子域（如订单、账户）。
结论：没有银弹。CQRS 是微服务查询中最推荐的模式，但它的适用边界需要仔细评估。优先从 API Composer 起步，当查询性能成为瓶颈或有复杂查询需求时，再引入 CQRS 的 View DB，并根据业务需要叠加 RYW 一致性。Event Sourcing 只在审计/溯源需求明确时才考虑。
