Production Readiness Review 生产就绪评审

PRR (Production Readiness Review) 是评估业务 workload 是否具备在生产环境安全、可靠运行能力的系统性评审过程。它覆盖从 SLI/SLO 定义到故障演练、变更管理、安全生产的完整维度，确保服务在云上部署前达到定义的成熟度标准。

核心理念：PRR 不是一次性的评审检查，而是一个持续改进的流程。服务随业务演进，PRR 标准也应随架构变化定期重新审视。最终目标是使服务具备 自愈能力（self-healing）和 持续合规（continuous compliance）。

1. SLI / SLO

SLI — Service Level Indicator
服务质量的量化度量。例如：请求成功率、P99 延迟、吞吐量。
SLO — Service Level Objective
SLI 的目标值或区间。例如：P99 延迟 < 500ms。
SLA — Service Level Agreement
与用户的契约性承诺，通常附带经济后果（赔偿/罚金）。
Error Budget — 错误预算
1 − SLO 的剩余空间。用于平衡可靠性与功能迭代速度。

常见 SLI 维度

关键实践

  • 从用户侧定义 SLI：优先选择直接影响用户体验的指标（如客户端延迟），而非仅收集服务端指标。
  • 错误预算机制：SLO = 99.9%，则错误预算 = 0.1%。SLO 达标时团队可以大胆发布；预算耗尽时冻结发布，全力提升稳定性。
  • 燃烧率告警：当错误预算燃烧速度过快时，应提前告警而非等到预算耗尽。
  • SLI 看板：每个服务必须有展示核心 SLI 的看板，看板必须对接告警通道。
  • 发布 SLO：向内部消费者发布 SLO，使其了解服务的可靠性边界，避免过度信任或信任不足。
纵深：不要只搜集"能搜集的"指标，而要搜集"能反映用户真实体验"的指标。服务端 P99 正常不代表客户端体验良好——网络延迟、DNS 解析、CDN 回源都可能引入额外延迟。

2. 可冗余 — Redundancy

消除单点故障 (SPOF)。每个组件至少需要两个独立副本。

2.1 SPOF 识别与消除

  • 每个关键组件必须识别其 SPOF，并提供缓解方案。
  • 常见 SPOF：单 DB 实例、单 AZ、单负载均衡器、单存储卷、单域名服务器。
  • 缓解策略：主备 (active-passive) 或 多活 (active-active)。

2.2 微服务多集群部署

  • 每个微服务至少部署在 2 个独立集群上（Kubernetes 集群或计算池）。
  • 集群间基础设施隔离：独立控制面、独立故障域。
  • 流量分发：DNS 权重、全局负载均衡器、服务网格路由。

2.3 反亲和部署

  • Pod 反亲和：同一服务的 Pod 副本调度到不同 Worker 节点。
  • 节点反亲和：工作负载分布在不同节点组 / 故障域。
  • 存储反亲和：有状态服务（数据库、消息队列）的存储卷分布在不同存储后端。
  • 实现方式：Kubernetes podAntiAffinity + topologySpreadConstraints。
YAML 示例：Kubernetes 反亲和配置 
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: my-service
        topologyKey: "kubernetes.io/hostname"
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: "topology.kubernetes.io/zone"
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: my-service

2.4 数据冗余

  • 副本跨 AZ 或跨 Region 分布。
  • 分布式存储：Replication Factor ≥ 3 or Erasure Coding。
  • 数据库：主从复制、Quorum 读写、跨区域同步。

3. 可容灾 — Disaster Recovery

从 AZ 级和 Region 级故障中存活并恢复的能力。

3.1 3AZ 部署

  • 服务和中间件至少部署在 3 个可用区。
  • 每个 AZ 是独立的故障域（供电、制冷、网络）。
  • 负载均衡器分发流量到所有 AZ；丢失任一 AZ 时保留 ≥ 66% 容量。

3.2 Region 级容灾

  • Region 切换：能够将全部流量从 Region A 切换到 Region B。需定期演练。
  • Region 演练：至少每季度执行一次完整的 Region 级故障切换演练。
  • Region 闭环：Region 内自我闭环——无跨 Region 运行时依赖。唯一跨 Region 的是异步数据复制。
  • 跨 Region 数据复制：根据 RPO 要求选择同步或异步复制。

3.3 DNS 与 API 网关

  • DNS：GSLB + 延迟/地理路由。TTL 设低（30–60s）以支持快速切换。
  • API 网关 (APIG)：统一入口，支持流控、鉴权、路由和 Region 级故障切换。

3.4 数据保护

  • 软删除：支持从误删除恢复。根据数据类型定义保留周期。
  • 备份：自动化备份，定义 RTO 和 RPO。备份存储在异 Region。
  • 数据一致性：复制/切换后校验数据一致性（Checksum、Reconciliation Job）。

3.5 DR 指标

指标典型目标说明
RTO (Recovery Time Objective)< 1 小时服务恢复所需时间
RPO (Recovery Point Objective)< 15 分钟最大数据丢失窗口
Failover 成功率100%（演练中）自动化验证
常见陷阱：主站点承载所有流量，备用 Region 从未被真正使用。当真正故障发生时，备用 Region 的配置可能已过时、容量不足、或中间件版本不一致。定期演练是唯一验证手段。

4. 可过载控制 — Overload Control

保护系统免受流量尖峰、慢客户端和下游故障的影响。

4.1 API 网关流控

  • 按消费者 / API / 方法设置速率限制。
  • 突发流量允许：Token Bucket 或 Leaky Bucket 算法。
  • 返回 429 Too Many Requests + Retry-After 头部。
  • 优雅降级：非关键 API 优先限流。

4.2 重试控制

  • 指数退避：基时每次翻倍，添加随机抖动（Jitter）避免惊群效应。
  • 重试预算：限制总重试次数（如最多 3 次）。耗尽后快速失败。
  • 熔断器 (Circuit Breaker)：连续失败超过阈值 => Open 态，拦截请求让下游恢复；定期探活（Half-Open）检测恢复。
重试策略对比
策略说明适用场景
立即重试失败后即刻重试网络包损坏等稀有瞬态故障
固定间隔固定延迟后重试服务短暂繁忙
指数退避 + Jitter延迟逐次翻倍 + 随机化通用场景，避免惊群
渐进式延迟线性增长特定速率限制场景

4.3 服务降级与自动扩缩

  • 优雅降级：过载时关闭非核心功能，返回缓存/过期数据而非错误。
  • 舱壁模式 (Bulkhead)：按消费者/租户隔离资源。一个舱壁内的故障不影响其他舱壁。
  • 自动扩缩：
    • HPA：基于 CPU / 内存 / 自定义指标。
    • Cluster Autoscaler：节点级扩缩。
    • 预测性扩缩：针对周期性流量模式。
    • 缩容应慢于扩容，以吸收流量波动。
enrich: Bulkhead 模式详解

Bulkhead（舱壁）模式得名于船舱水密隔舱设计——一个隔舱进水不影响其他隔舱。

在分布式系统中的应用：

  • 资源隔离：每个下游服务分配独立的连接池/线程池。Service A 故障时，只有它的池被耗尽，Service B 和 C 不受影响。
  • 实例隔离：每个租户使用独立的服务实例。Client 1 流量过大只会打满自己的实例。
  • 队列隔离：异步消息使用独立的队列和消费者组。
  • 工具：Resilience4j (Java)、Polly (.NET)。

5. 可故障管理 — Fault Management

检测、响应、学习故障。

5.1 健康检测

  • 主节点监控：通过 Lease / Heartbeat 检测 Leader 故障。
  • 备节点监控：备节点常被忽视。必须同样积极地监控备节点健康。定时对备副本执行健康检查和查询测试。
  • Liveness vs Readiness：Liveness 探针重启不健康 Pod；Readiness 探针将不健康 Pod 从服务中移除。

5.2 主备切换

  • 自动化故障切换：Pacemaker、Kubernetes Leader Election、数据库 HA Manager。
  • 优先选择 Active-Active 方案——无切换延迟，降低 Split-Brain 风险。
  • 文档化切换流程并定期演练。

5.3 故障模式库与演练

  • 维护故障模式库：列出所有已知故障模式、症状、检测方法、缓解步骤、升级路径。
  • 常见故障模式：网络分区、节点故障、AZ 故障、慢查询、证书过期、OOM、磁盘满、数据损坏。
故障模式库模板
故障模式症状检测缓解
Pod OOMKilled容器重启，错误率上升Kubernetes events + metrics调大 limits，检查内存泄漏
DB 连接池耗尽API 超时，连接错误DB 连接数监控增加 max_connections，优化连接池
证书过期TLS 握手失败证书到期前 30d 告警自动续签 (cert-manager)
AZ 故障某 AZ 实例全部不可达AZ 级健康检查切除该 AZ，流量发往其他 AZ

混沌工程 (Chaos Engineering)

  • 定期注入故障来验证系统行为。
  • 工具：Chaos Mesh（Kubernetes 原生）、Litmus、Gremlin、Azure Chaos Studio。
  • 注入类型：Pod 删除、网络延迟/丢包、CPU/内存压力、磁盘 I/O 故障、DNS 故障。
  • 原则：从小爆炸半径开始，逐步扩大。
  • Game Days：计划性演练，团队在注入故障上实践应急响应。
enrich: Chaos Mesh 架构与工作流

Chaos Mesh 是 CNCF 孵化的混沌工程平台，基于 Kubernetes CRD 构建：

  • Chaos Dashboard：可视化 Web UI，管理实验、RBAC 权限。
  • Chaos Controller Manager：核心调度逻辑，管理多种 CRD Controller。
  • Chaos Daemon：以 DaemonSet 模式运行，注入具体故障（网络、文件系统、内核）。

典型工作流：用户在 Dashboard 定义实验 → API Server 创建 Chaos CRD → Controller Manager 调度 → Daemon 注入故障。

6. 可变更能力 — Change Management

安全、渐进地交付变更，每个阶段具备可观测性。

6.1 部署策略

策略描述适用场景
滚动更新 (Rolling)逐个替换 Pod无状态服务，低风险变更
蓝绿部署 (Blue-Green)两套完整环境，流量一次性切换高风险变更、有状态迁移
灰度 (Canary)逐步将流量切换到新版本用户侧服务、A/B 测试

6.2 Ring 环灰度

Ring 0 (dev/test) → Ring 1 (内部试用) → Ring 2 (区域灰度1-5%) → Ring 3 (逐步扩大) → Ring 4 (全量)
  • Ring 0：开发/测试环境部署，内部验证。
  • Ring 1：公司内部用户，Dogfooding。
  • Ring 2：小规模外部用户（1-5%）。
  • Ring 3：逐步提升流量百分比。
  • Ring 4：100% 生产流量。
  • 每个 Ring 有 浸泡期（如 30 分钟），期间监控 SLO 和 Error Budget。
  • 拨测 (Synthetic Probing)：在每个 Ring 上线前运行自动化探测。

6.3 集群级灰度

先将新版本部署到一个集群验证，确认无误后再部署到其他集群。

6.4 节点级分批变更

基础设施变更（OS 升级、内核补丁、Agent 更新）：逐节点或分批（如每批 10%）滚动。每批后监控关键指标，发现回退则暂停。

6.5 特性灰度 (Feature Flags)

  • 将部署与发布解耦。特性可按用户、Region、租户开关。
  • 特性开关系统支持：渐进式发布、A/B 测试、即时关闭。
  • 特性全面上线后移除 Flag，避免技术债。
纵深：Google SRE 实践——每个 Ring 的浸泡期不仅仅是"等一会儿"，而是持续验证 SLO 燃烧率不超过预期。如果一个 Ring 在浸泡期内消耗了超过 2% 的月度错误预算，则阻断该 Ring 的推进。

7. 可运维 — Operability

从第一天就为运维而设计。

7.1 数据面不依赖管理面

  • 数据面（服务用户流量）必须在管理面（部署、可观测性、配置）不可用时继续运作。
  • 管理面故障不得引起数据面降级。
  • 设计原则：管理面组件不应处于用户请求的关键路径上。

7.2 监控与告警

  • 四大黄金信号 (Google SRE)：延迟 (Latency)、流量 (Traffic)、错误 (Errors)、饱和度 (Saturation)。
  • 多级拨测：
    • L1：基础可用性（Ping / Health Endpoint）。
    • L2：功能探测（登录、搜索、下单等业务流程）。
    • L3：业务事务探测（端到端 + 数据校验）。
  • 告警等级：
    等级响应时间示例
    P0≤ 5 分钟服务不可用、数据丢失
    P1≤ 15 分钟P99 延迟 > 2x 基线
    P2≤ 1 小时错误率轻度升高
  • On-Call：建立 Primary/Secondary 轮值。Google SRE 建议：≤ 25% 时间 On-Call，≥ 50% 用于工程改进。
  • Runbook：每种告警类型文档化排障步骤。Runbook 应版本控制并定期测试。

7.3 日志与可观测性

  • 结构化日志（JSON），跨服务关联 Trace ID。
  • 分布式追踪：OpenTelemetry、Jaeger、Zipkin。
  • 指标：Prometheus + Grafana 或云厂商托管方案。
  • 日志聚合：ELK、Loki、或云原生方案。
enrich: 黄金信号实战建议
  • Latency：区分"正常响应时间"和"超时/错误"。确保 P50/P95/P99 各自独立监控。
  • Traffic：不仅看总量（QPS），还要看每个 Consumer/Tenant 的分量，用于限流和成本分摊。
  • Errors：区分客户端错误（4xx）和服务端错误（5xx）。5xx 才是黄金信号里的"Errors"。
  • Saturation：最容易被忽略的信号。CPU 100% 是饱和的晚期信号；线程池队列深度、内存使用率、磁盘 IOPS 饱和是更早的预警。

8. 安全生产 — Production Safety

安全运维的管控与治理。

8.1 审计日志

  • 所有生产访问和变更必须可审计。
  • 记录内容：谁、做了什么、何时、从哪、对什么资源。
  • 不可篡改存储：审计日志写入 Append-Only 存储（S3 Object Lock、SIEM 系统）。
  • 保留周期：按合规要求（通常 ≥ 1 年，金融行业 ≥ 7 年）。
  • 权限审查：定期审查生产访问权限，最小权限原则。

8.2 变更审批

  • 生产变更必须有定义的变更管理流程。
  • 紧急变更需要事后审查和合理性说明。
  • 所有 Infrastructure-as-Code 变更需要 Peer Review。

8.3 密钥管理

  • 禁止在代码或配置文件中存储凭据、Token、密钥。
  • 使用密钥存储：HashiCorp Vault、Cloud KMS、Kubernetes Secrets（开启加密）。
  • 按计划自动轮换密钥。

8.4 合规

  • 数据驻留要求：数据存储在指定 Region。
  • 传输中加密 (TLS) 和静态加密。
  • 依赖漏洞扫描：SBOM、CVE 监控。
  • 定期渗透测试。

9. 评审节奏与清单

何时触发 PRR

  • 新服务首次生产部署前。
  • 重大架构变更（新增 Region、变更数据存储、重大重构）。
  • 重大事故后，发现架构性安全/可靠性缺口。
  • 现有服务年度复评。

检查清单格式

每个 PRR 项目应有以下要素：

  • 要求描述：需要满足什么。
  • 验收标准：可测量 / 可验证。
  • 证据：看板 URL、配置片段、测试结果。
  • 责任人：谁负责。

成熟度模型评分

等级含义
L0 — 未处理未考虑此维度
L1 — 人工依赖人工操作，无自动化
L2 — 部分部分自动化，有残留风险
L3 — 完成全自动化、文档化、已验证
L4 — 持续自愈能力、持续验证
PRR 检查清单示例（部分）
  • 是否定义了 SLI 看板并对接告警？
  • 是否存在 SPOF？是否已识别并缓解？
  • 服务是否部署在 ≥ 2 个集群？
  • 是否配置了 Pod 反亲和和 TopologySpread？
  • 中间件是否跨 3AZ 部署？
  • 是否定期执行 Region 故障切换演练？
  • API 网关是否配置了流控？
  • 是否实现了 Circuit Breaker + Retry 模式？
  • 是否存在故障模式库？是否定期进行 Chaos Engineering 演练？
  • 变更是否经过 Ring 灰度 + 浸泡 + 拨测？
  • 数据面是否独立于管理面？
  • 是否配置了多级拨测？
  • 审计日志是否启用并配置了不可篡改存储？
结论：PRR 不是一次通过就一劳永逸的检查。系统会老化、依赖会变更、业务需求会进化。建议每季度审视 PRR 检查项，将 PRR 整合进 服务生命周期管理 流程中。目标不是一个完美无缺的系统，而是一个 已知风险可接受、故障可发现、恢复可预期 的系统。
