BOT Agent vs. Traditional Alert

特征 传统告警系统（Alerting） AI 智能体（AI Agent）
核心机制 基于硬编码规则和阈值 基于 LLM 的推理、规划和工具调用
触发方式 某个指标超过预设值（例如：CPU > 90%） 接收到复杂指令或检测到异常模式（例如：发布事件开始）
输出结果 简单的通知（邮件、短信、PagerDuty） 结构化的分析报告、RCA 和自主行动
思维能力 无。仅判断 True/False 有。能分解任务、制定计划、反思、自我修正
对数据的处理 仅关注单个指标是否超过阈值 能够综合分析多个指标（延迟、错误率、日志、基线）之间的复杂关系。这是核心，因为 LLM 具有核心知识
行动能力 主要是通知人来解决 可以调用 API 执行 rollback()、isolate_traffic() 或 auto_fix() 等复杂操作
主要目标 通知 SRE/DevOps 发生了什么问题 解决 为什么 发生问题，并主动处理
Agent vs 传统告警：从"告诉我出事了"升级为"告诉我为什么出事并主动处理它"。核心差异在于 LLM 能综合多维度数据做推理，而非仅依赖单指标阈值。

Prompt vs. Program

纯提示词构建的 Agent：稳定性和可靠性不够。

用 Agent SDK 构建的 Agent：稳定性和可靠性会强很多。

知识库 Agent 中的对比

维度 纯 Prompt 方式 编程方式
搜索范围 自主扩张搜索范围。某些场景下是优势（如 explore subagent 不断 grep 不同词获取信息） 可控，由代码限定数据源
数据源校验 搜索到不良数据源时，可用 GAN subagent 验证 可直接校验 MCP Tool 查找的 Wiki 数据源，可靠性更高
定量处理 无法强制做定量处理 可强制做定量处理，如 Wiki 搜索排序和打分

结论：编程方式提供更高的可靠性，特别是在数据源校验和定量处理方面。但纯 Prompt 方式在某些探索性场景（如 explore subagent）有灵活性优势。

Evidence Quote Gate

对每个输出字段标注允许的证据来源，是目前看到的最精细的反幻觉模式。

推理过程透明

Code Review Agent 经验

架构概览

Code Review Agent 使用了并行的多 Agent 从不同方面进行 Review，结合确定性脚本获取上下文和 IO + LLM 判断的模式。

确定性脚本层

使用 Preflight 脚本先获取所有的 Review 上下文：

步骤 说明
Repo 获取 拉取代码仓库
Agent Repo 获取 获取 Review Rule 等配置
GraphQL 拉取评论线程 获取 PR 上的已有讨论
并行获取 上下文失败直接退出（diff）
多层 Rule 后面覆盖前面，支持层级化规则

使用 publish.py 来统一发布评论。

Subagent 视角分工

不同的 Subagent 从不同专业视角进行 Review，例如架构、安全性、性能、代码风格等。

Delta-Only 原则

核心思路：只报告本次变更引入的新问题。

这解决了 AI Review 最大的噪音源：对已有问题的重复报告。

GAN Peer-Review

使用 GAN（生成对抗网络）模式的 Debate Agent 来辩论和验证发现：

  • 一个 Agent 提出 Review 发现
  • 另一个 Agent 作为对手方质疑
  • 提升 Review 的准确性和鲁棒性

机制 说明
Re-evaluate 机制 提供 Loop 功能。当 PR 作者回复 AI 评论质疑 finding 时，Pipeline 走 re-evaluate 路径重新评估
PR 作者质疑 质疑触发重新评估流程，而非直接驳回

Rule 的设计

有效的 Rule 设计包含以下要素：

## Checkpoint N: [问题名称] [Severity]
触发条件 (when)
检测逻辑 (what to check)
代码示例 (正例 / 反例)
Do NOT flag (排除条件)

设计要点：

  • 明确定义级别：每条规则有清晰的分级
  • 加入代码示例：同时提供正例和反例
  • 同一条规则也分级：不同严重级别有不同处理方式
Code Review Agent 的核心经验：确定性脚本保证上下文质量 + 多 Subagent 视角分工 + Delta-Only 消除噪音 + GAN 模式提升准确性 + 完善的 Rule 体系提供可操作性。
